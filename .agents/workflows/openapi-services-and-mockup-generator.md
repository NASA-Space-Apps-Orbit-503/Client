# OpenAPI service and mock generator

## Goal

When updating `openapi/api/openapi.yaml`, keep the mocks in `data/` and the services in
`app/services/` synchronized. Services must use the typed client generated by
`nuxt-open-fetch` and allow switching between the real API and fake data through `USE_MOCKS`.

## Agent instructions

1. Read `openapi/api/openapi.yaml` and list all routes, operations, `operationId` values,
   parameters, request bodies, and response schemas.
2. Generate the Nuxt types (`pnpm nuxt prepare`, or the project-configured equivalent) and
   use the resulting types from `#open-fetch-schemas/api`. Do not manually duplicate contract
   types in the services.
3. Group operations by entity/tag and create or update one
   `app/services/<entity-name>.service.ts` file per entity. Preserve existing file names and
   use kebab-case for compound entities.
4. Every service function must:
   - Have a TypeScript signature compatible with the generated schema.
   - Read `useMocksEnabled()` before making the request.
   - Return the corresponding mock when `USE_MOCKS=true`.
   - Otherwise use the generated client:
     `const { $api } = useNuxtApp(); return $api('<route>', <options>)`.
   - Pass parameters in `query` or `path`, request bodies in `body`, and the correct HTTP
     method.
5. Create or update one JSON file in `data/` for each mock response used. Values must be
   fake, valid according to the contract, and cover required fields, nullability, enums, and
   paginated structures.
6. If an operation returns CSV, keep a CSV text mock and the corresponding `content-type` in
   the real request.
7. Keep `runtimeConfig.public.useMocks` in `nuxt.config.ts` connected to `USE_MOCKS` (and
   compatible with `NUXT_PUBLIC_USE_MOCKS`). Update `.env.example` if the variable name
   changes.
8. Check that no contract routes or operations lack a required service or mock. Remove or
   rename obsolete mocks only when they are no longer referenced.
9. Run `pnpm lint`, `pnpm typecheck`, and service-specific tests if the project includes them.
   Fix type errors without using `any` or suppressing errors.

## Acceptance criteria

- Services cover all functional operations in the contract.
- `USE_MOCKS=true` does not require the API to be available.
- `USE_MOCKS=false` uses only `$api` with contract-defined routes and parameters.
- Mocks comply with the generated types and contain no real data or secrets.
